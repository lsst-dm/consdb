##################
Alembic Migrations
##################

`Alembic <https://alembic.sqlalchemy.org/>`__ applies the schema changes to the database.
This page gives the layout of the migrations in this repository.
The :doc:`../operator-guide/schema-migration-process` page gives the procedure that makes and applies a migration.

One tree for each schema
========================

Each ConsDB schema has its own directory under ``alembic/`` and its own section in ``alembic.ini``.
The section name is the value that you give to the ``-n`` option of every ``alembic`` command.

.. list-table::
   :header-rows: 1
   :widths: 30 30 40

   * - Section (``-n``)
     - Schema
     - Note
   * - ``latiss``
     - ``cdb_latiss``
     -
   * - ``lsstcomcam``
     - ``cdb_lsstcomcam``
     -
   * - ``lsstcomcamsim``
     - ``cdb_lsstcomcamsim``
     -
   * - ``lsstcam``
     - ``cdb_lsstcam``
     -
   * - ``startrackerfast``, ``startrackernarrow``, ``startrackerwide``
     - ``cdb_startracker*``
     - One revision each. Not in use.
   * - ``efd_latiss``, ``efd_lsstcomcam``, ``efd_lsstcam``
     - ``efd_*``
     - The Transformed EFD data. The schema name has no ``cdb_`` prefix.
   * - ``efd_scheduler``
     - ``efd_scheduler``
     - The task records of the Transformed EFD service.

Each directory has its own ``env.py``, ``script.py.mako``, and ``versions/`` directory.
The revision graphs are independent.
A revision identifier in one tree means nothing in another tree.
The ``head`` of each tree is therefore different, and ``alembic upgrade head`` must run once for each tree.

The version tables
==================

Alembic records the current revision of each tree in a table named ``<schema>_version``.
For the ``cdb_*`` trees the table is in the ``cdb`` schema, for example ``cdb.cdb_latiss_version``.
For the ``efd_*`` and ``efd_scheduler`` trees it is in the ``efd`` schema, for example ``efd.efd_scheduler_version``.
There is no ``alembic_version`` table.
To read the revision of a schema directly:

.. code-block:: sql

   SELECT version_num FROM cdb.cdb_latiss_version;

The ``cdb`` schema, the ``pg_sphere`` extension, and the ``usdf`` and ``oods`` roles must exist before the first ``cdb_*`` migration, and the ``efd`` schema before the first ``efd_*`` migration.
``docker/alembic-setup.sql`` creates the ``cdb`` set for the local Compose stack, and ``alembic-autogenerate.py`` creates it in its temporary database.
Neither creates the ``efd`` schema; create it by hand before you run an ``efd_*`` tree against a new database.

What ``env.py`` does
====================

Every ``env.py`` follows the same pattern.

1. It reads ``CONSDB_URL`` for the database and ``SDM_SCHEMAS_DIR`` for the schema files.
   It stops with an error if either is not set.
2. It loads ``$SDM_SCHEMAS_DIR/yml/<schema>.yaml`` with `Felis <https://felis.lsst.io/>`__ and builds the SQLAlchemy metadata from it.
   In the ``sdm_schemas`` repository, ``yml`` is a link to `python/lsst/sdm/schemas <https://github.com/lsst/sdm_schemas/tree/main/python/lsst/sdm/schemas>`__, where the ConsDB files are the ``cdb_*.yaml`` and ``efd_*.yaml`` files.
3. It calls ``add_shadow_column()`` from ``lsst.consdb.cdb_pgsphere``.
   This adds the ``pgs_region`` column to the ``exposure`` and ``ccdexposure`` tables.
   The column is a *shadow column*: it exists in the database primarily for the ``consdbtap`` service, and it is not in the YAML files or the schema browser.
   The metadata must gain it here, or autogenerate would produce a migration that drops it.
4. It limits the comparison to the one schema of the tree, and it excludes the ``visit1`` and ``ccdvisit1`` views from the comparison.
   Alembic cannot compare a view with a table definition.
   Steps 3 and 5 apply to the ``cdb_*`` trees only; the ``efd_*`` schemas have no views and no shadow column.
5. It generates the SQL that drops and creates the two views, and the ``GRANT SELECT`` statements for the ``usdf`` and ``oods`` roles.
   It stores this SQL in ``context.config.attributes``, from which ``script.py.mako`` copies it into every new revision.

Step 5 is the reason that every autogenerated revision contains the view statements.
The migration process asks you to remove them when the ``exposure`` and ``ccdexposure`` tables do not change.

The autogenerate script
=======================

``alembic-autogenerate.py`` at the top of the repository makes a revision for a schema change.
For each tree it starts a temporary PostgreSQL instance, prepares it as above, upgrades the tree to ``head``, and runs ``alembic revision --autogenerate``.
The new revision is the difference between the head of the tree and the YAML file.

.. important::

   With no ``--instrument`` option, the script processes ``latiss``, ``lsstcomcam``, ``lsstcomcamsim``, and ``lsstcam`` only.
   For a change to an ``efd_*``, ``efd_scheduler``, or ``cdb_startracker*`` schema, give ``--instrument`` with the section name.

Alembic runs Black on each new revision file, with the line length of the repository.

The migration validator
=======================

``tests/validate_schema_migrations.py`` checks a new revision in three ways: that autogenerate now produces an empty revision, that an upgrade and a downgrade in a temporary database match the new and the old YAML files, and, if ``CONSDB_URL`` is set, that two full cycles against that database succeed.
The :doc:`../operator-guide/schema-migration-process` page gives the command.

The script exits with status 1 when it finds a difference, and it writes ``validate_schema_debug.json`` at the top of the repository.
The file lists the differences that Alembic found, in the order of the three checks, and the primary, unique, and foreign keys that it read from the database.
Read the first difference first.
A difference in the first check usually means that the revision does not match the YAML.
A difference in the third part of the second check means that ``downgrade()`` does not undo ``upgrade()``.

The ``--keep-delete-me`` option keeps the empty revision that the first check generates, so that you can read it.
Delete it before you commit.

Useful commands
===============

All commands run from the top of the repository, with ``CONSDB_URL`` and ``SDM_SCHEMAS_DIR`` set.

.. code-block:: bash

   alembic -n latiss current            # the revision in the database
   alembic -n latiss history            # the revisions in the tree
   alembic -n latiss upgrade head       # apply all revisions
   alembic -n latiss upgrade head-1     # apply all but the last
   alembic -n latiss downgrade -1       # undo the last revision

If the database records a revision that no longer exists in the tree, for example after you delete a revision from a branch, ``alembic`` refuses every command.
Check that the schema in the database matches a revision that does exist.
Then record that revision without running anything:

.. code-block:: bash

   alembic -n latiss stamp --purge <revision>

Only do this against a database that you control.
